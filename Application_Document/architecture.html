01

System shape

The engine is two halves joined by one object. Phase A works out what the user wants and what every available source knows about it, and compresses that into a single Contract Knowledge Object. Phase B reads only that object and produces a document.

The split is the architecture. Phase B never sees the uploaded file, the clause library or the playbook — if it needs a fact, that fact belongs in the CKO. A test asserts the drafting engine's signature is exactly (cko, ctx), because the failure it prevents is someone adding template= under deadline and quietly ending the two-phase design while the diagrams still show it.

02

A request, end to end

The HTTP request never waits for a model. POST /contracts returns 202 with a run id and a stream URL; the run lives in a background task that owns the run row and the event log. A dropped connection, a proxy timeout or a refreshed tab cannot abandon a run that is spending money.

1

Intake

Request and uploads arrive. An upload marked as template is parsed immediately and stored as a blob with a workspace pointer — a corrupt or tracked-changes DOCX is refused while the user is still watching. Everything else is extracted to text as a reference.

api/routers/contracts.py api/uploads.py knowledge/providers/template.py
2

Launch

A Run row is created and a background task starts. The runner is thin: it maps an outcome to a run status and never touches the response.

api/runner.py api/pipeline_adapter.py
3

Pipeline

Phase A then Phase B, emitting a stage event at each step. Control paths — a question, a spent budget — return an outcome rather than raising; only a genuine fault propagates.

pipeline.py stage events → SSE
4

Streaming

Events are persisted first, notified second. A client reconnects with ?seq=N and replays the gap from Postgres, so a blip cannot lose an event that was never written.

api/events.py api/routers/runs.py
5

Settlement

The adapter records the contract type, mirrors the draft into the workspace where the preview reads it, stamps the winning version finalized, sets the review flag when placeholders remain, and emits the terminal event.

api/pipeline_adapter.py workspace/store.py

Asking is a suspension, not a pause.

No process blocks on a human. When a stage needs clarification it persists the questions, commits, and raises — the run slice ends. Answering starts a new run that folds every previous answer back into the request and re-enters Phase A. The rule for callers is one line: commit what you need, then ask, and let the ask be the last thing you do.

03

Phase A — building knowledge

00

Intent Agent

Reads the request and reports what was asked for: contract type, parties, governing law, purpose, and deal terms captured verbatim — the operative numbers, which is the only route by which "99.9% uptime" reaches the drafter. Asks when the model requested clarification or confidence is below 0.7. Any contract type is accepted; there is no allow-list refusal.

phase_a/intent.py gpt-4.1-mini · temp 0 00-intent.json
—

Consent gate

Runs after resolution, when it is actually known whether approved clauses exist. If neither the clause library nor a template backs the draft, the run stops once and discloses: the wording will come from the model's own legal knowledge and has not been reviewed. The decision is recorded in the workspace, so the resumed run — which re-enters Phase A from the top — does not ask again.

phase_a/consent.py consent/model-knowledge.json no model
01

Knowledge Source Resolver

Asks every registered provider whether it has anything for this run, then orders the survivors by fixed precedence. A plan may narrow precedence but never reorder it — precedence decides who wins a conflict, and that is policy, not a per-run judgement.

phase_a/resolver.py no model 01-resolution-plan.json
02

Providers contribute

Each resolved provider returns a contribution in one shared vocabulary. The template provider parses the DOCX into blocks with stable fingerprints; the reference provider analyses documents into knowledge, never text to copy.

phase_a/gather.py knowledge/providers/ ×5 02-template.json
03

Understanding engine — three agents, one parse

Template mode only. Semantic structure, metadata and clause classification run in parallel over a single parse. They return their objects; the caller writes all three artifacts sequentially afterwards, because concurrent workspace writes would contend on the same advisory lock.

phase_a/understanding.py understanding · gpt-4.1 metadata · mini classification · gpt-4.1
04

Aggregator

A pure function — no model, no I/O. Merges contributions by precedence. Where two sources disagree it records both values and both provenances rather than silently picking one.

phase_a/aggregator.py phase_a/build_cko.py pure 04-cko.json

04

The Contract Knowledge Object

Everything Phase A understood, in one versioned object: intent and its deal terms, the resolution plan, semantic sections, metadata, clause candidates, playbook rules, a formatting manifest, and provenance for each. It carries schema_version from day one and ignores unknown fields, because the schema will be wrong at first and that must not be a migration event.

The boundary is mechanical, not aspirational.

run_drafting_engine(cko, ctx) takes one knowledge parameter. One test asserts the parameter set is exactly {cko, ctx}; another walks the AST to prove phase_b/** reaches Phase A only through the CKO schema, and that neither phase imports an agent framework. Adding a CKO field is routine. Adding a Phase B parameter is a design review.

05

Phase B — drafting

Five stages in a load-bearing order. The transformation plan must exist before drafting, and it must be a reasoned artifact rather than an afterthought.

05

Draft Planning Agent

Decides what sections the contract should have and why, before a word is written. Each records where it came from — library, playbook, or model.

phase_b/planning.pygpt-4.1-mini05-draft-plan.json
06

Transformation Planning

Classifies every section into KEEP / MODIFY / REMOVE / ADD. In template mode a model decides, given the CKO alone. In generation mode there is no source document to classify against, so the plan is derived from the draft plan — every planned section becomes an ADD. That derivation is deliberate: asking a model to classify sections that do not exist once lost seven of eight sections.

phase_b/planning.pygpt-4.1 · temp 006-transformation-plan.json
07

Clause Recommendation

Retrieve → rank → recommend. A deterministic scoring function, no model. Records the chosen clause, the rejected alternatives, and why.

phase_b/recommendation.pyinvariants/ranking.pydeterministic
08

Drafting Agent → document

Writes clause text and recitals only. Everything else a contract needs — title, party block, execution page — is fact and is derived from the CKO. The agent produces text, never a document: assembling and numbering is deterministic code, because that has a right answer.

phase_b/drafting.pyphase_b/document.pyinvariants/docx_build.pygpt-4.1 · temp 0.2

Legal & Document validation

Two independent gates, both run, both persisted. Legal asks whether the contract is correct; document asks whether it is well-formed.

The document model

A contract is a tree, not a blob of Markdown. Only clauses are numbered — Word computes 1. → 1.1 → (a) → (i) from an injected multilevel definition, so nothing types a number into text and inserting a clause renumbers the rest automatically. Preamble, recitals and the signature block are deliberately unnumbered; a numbered WHEREAS is the clearest tell that a machine assembled the document.

06

Two modes, one gate

The mode is read off the CKO — source_storage_key is present if and only if a document was uploaded — never passed in as a flag.

Mode 1 · generation

Built from the plan

Nothing to preserve, so the document is assembled from the drafted sections in plan order.

  1. Draft plan names the sections.
  2. Transformation derived — all ADD.
  3. Agent writes clause text and recitals.
  4. render_contract() builds the DOCX with real Word numbering.
  5. Both gates run.
Mode 2 · template

The original, edited in place

The uploaded document is the knowledge. It is edited from its own bytes — never regenerated.

  1. DOCX parsed into blocks with stable ids.
  2. Understanding engine reads its meaning.
  3. Transformation decides per block.
  4. apply_transformation() changes only MODIFY / REMOVE / ADD.
  5. Fidelity check, then both gates.

Fidelity, measured on a real run

The export serves stored bytes.

Phase B's DOCX is kept in blob storage, pointed at by contract_versions.docx_storage_key. The export serves those bytes. Regenerating from markdown at download time would discard the formatting the upload existed to preserve — a perfect in-place edit thrown away at the last step.

07

Gates — what stops, what flags

One path to a finished document, through both validators. The distinction that matters: a blocker means the document is wrong; a flag means it is incomplete but useful. A flagged draft still finalizes and downloads.

ConditionOutcomeWhy
Reference text copied verbatimblocksattached documents are read for context, never reproduced
Required playbook section missingblocksthe contract is not the one policy required
Planned section absent from the draftblockscaught a run that finalized 1 of 8 sections
KEEP section's formatting disturbedblocksthe Mode-2 promise, checked at the finish line
Upload carries tracked changesrefused at intakeaccepting mutates a legal document with no audit trail
Fill-in placeholders remainflagsa labelled gap is a legitimate first draft
Numbering gap · dangling cross-referenceflagsworth a look, not worth refusing the document
Both reports cleanfinalizedstamped; only a stamped version can be exported
Placeholders were once a blocker. That was wrong.

Refusing a draft because it contained [MONTHLY RENT] turned "draft a lease" into a dead end — the opposite of what a drafting assistant is for. They are now a flag: the draft finalizes, the version is marked for review, and the slots are listed by name so the user knows exactly what to complete. What must never happen is a placeholder shipped silently, and a finalized-but-flagged draft with its gaps named is the opposite of silent.

The validators are framework-free. A test walks the import graph of backend/invariants/** and fails if it imports agents, openai, langchain, langgraph or deepagents. The checks that decide whether a contract may exist cannot depend on a model being in a good mood.

08

Stop conditions

All enforced in code. A prompt asking an agent to stop is not a stop condition — the engine learned this the hard way when an agent that kept reporting 30% confidence asked the same question five times while the user kept answering.

SettingValueWhat it prevents
max_ask_rounds3an endless question loop; counted from the ledger, since a suspension ends the process
max_draft_attempts3a redraft cycle that never converges
max_turns40a wedged agent burning turns
intent_confidence_threshold0.70drafting the wrong contract type confidently

Answers accumulate. Every resume folds in every previously answered round, each question paired with its answer, prefixed "treat these as established facts and do not ask them again". Folding in only the latest round — which the engine once did — discards everything the user already said, and is what makes a loop feel infinite.

The workspace is a per-contract virtual filesystem in Postgres, with read-only prefixes (clauses/, skills/, playbooks/) and advisory locks. Binary documents live in blob storage; the workspace holds a small JSON pointer, because a 10 MB DOCX in a text column would be loaded by every listing that touches the row.

Two things the design will not trade.

Never invent a fact about the deal. Not a party, a date, a fee or a term. Values the user states are captured at intent time and carried through the CKO to the drafter; a value that is missing becomes a question, or a labelled placeholder — never a plausible guess.

The tools are authoritative over correctness. There is no path to a document that goes around the gates — not through an agent, not through an HTTP client. A draft that fails is retained and explained, but it is not stamped.
